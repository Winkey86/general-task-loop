# План реализации General Task Loop

## Устройство

Пакет состоит из Markdown-инструкций и YAML-политики явного вызова. Пользователь устанавливает оба каталога `skills/` через ссылки на один checkout. Общий формат состояния, разрешения, ревью и протокол передачи описаны один раз в `skills/my-task-loop/references/workflow.md`.

## Шаги реализации

1. Адаптировать `my-task-loop` для произвольного репозитория, оформить этапы и шаблон постановки. Задать вход и выход каждой части Spec Kit и описать ручной путь.
2. Адаптировать `sam-reshu` со ссылкой на общий протокол. Описать начальное согласование, компактный план, самоприёмку и остановку при блокере.
3. Описать установку, вызов, передачу задачи и передачу разработки в README. Связать постановку, спецификацию, план и задачи.
4. Проверить ровно два `SKILL.md`, их метаданные, ссылки, состав публикации и отсутствие чувствительных данных. Проверить обнаружение обеих команд через локальные каталоги клиентов и сверить опубликованное дерево.

## Проверка по сценариям

| Сценарий | Что проверять при изменениях |
| --- | --- |
| US1 | Замечание оставляет текущий этап открытым. Команда переводит на следующий. В обоих путях Spec Kit получаются связанные требования, план и задачи. |
| US2 | После согласования цикл идёт самостоятельно. Локальный результат возможен без PR/MR. Для push остаются в силе согласованные ветка и репозиторий. |
| US3 | Состояние указывает на текущую ветку, правки, артефакты и следующий шаг. При смене цикла сохраняются решения и пределы авторизации. |

## Передача разработки

Начни с `postanovka.md` и таблицы выше. Найди состояние работ в `tasks.md`. При изменении механики обнови критерий в `spec.md` и соответствующую инструкцию. Оба клиента должны читать один и тот же комплект файлов. Проверку публикации выполняй по списку путей и хешам коммита.
